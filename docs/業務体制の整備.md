
## 🧭 目的

> 突発的なヘルプデスク対応の属人化を解消し、**業務処理速度の向上**と**チーム全体の負荷分散**を実現することで、各メンバーのプロジェクト遂行力とユーザー対応品質の両立を図る。
> 

---

## 🎯 目標

> 「対応体制の可視化と判断基準の共有により、現行タスク管理体制と共存可能な柔軟なヘルプデスク体制を整備する」
> 

### ✅ 数値指標目標

> 「60%以上のヘルプデスク対応が属人依存なく、定義された体制・判断基準に基づいて処理される仕組みの整備」
> 

（数値に関しては仮設定、実際のタスクの進行によって適切な値へ調整される見込み）

## 🧩 プロジェクトでやるべきこと

### ① 業務範囲・体制・担当者の明確化

| タスク案                 | 内容の例                                                                 | 備考                                   |
| ------------------------ | ------------------------------------------------------------------------ | -------------------------------------- |
| 業務棚卸し               | 日常・突発対応業務をリストアップし、対応の有無・優先度を分類             | 対象業務のスコープ把握                 |
| 現行担当者可視化         | 現状誰が担当しているかをマッピング（対応可能者・判断者など）             | 既存ワークフローとの整合確認にも       |
| サブカテゴリ設計         | 例えば「ネットワーク系」「端末系」「アカウント系」など業務をカテゴリ分け | 対応割り当てルールの下地に             |
| 担当者と代替者の役割定義 | 1次対応者・補佐・エスカレーション先を可視化                              | 「属人性を受け入れた上での透明性」確保 |
| 新業務体制・範囲の設計   | GoogleSheet, Notionなどの運用手段を選定                                  | メンテナンス性を意識した運用が重要     |

---

### ② レポートラインの構築

| タスク案                 | 内容の例                                                                       | 備考                             |
| ------------------------ | ------------------------------------------------------------------------------ | -------------------------------- |
| 対象イベントの定義       | レポート対象となる「報告すべき出来事」を定義（例：対応遅延、エスカレート案件） | 報告基準の明文化が主目的         |
| 報告項目のテンプレート化 | 誰が・何を・いつ・誰に・どうやって報告するかを標準化                           | Slack or フォーム報告等          |
| ケース別フロー設計       | 例：小規模障害・部署間連携案件などのパターンごとの報告ステップ設計             | 「どう判断するか」も含めて設計   |
| レポート管理の方法決定   | 報告ログの保管場所（例：Notion、スプレッドシート）と運用ルール定義             | 担当交代時の引継ぎ容易化にも寄与 |
| トライアル運用           | 1週間など短期間の試験運用で実用性・属人性排除効果を確認                        | 改善余地の抽出フェーズとして有効 |

## 🗂 サブプロジェクト構造化図（タスク構造マップ）

```jsx
① 業務範囲・体制・担当者の明確化（サブプロジェクト）
├─ 業務棚卸し
│  ├─ 日常・突発対応業務をリストアップする
│  ├─ 業務分類ルール（対応有無・優先度）を定義する
│  └─ 業務リストのレビュー・調整を行う
│ 
├─ 現行担当者可視化
│  ├─ 各業務に対する担当者をマッピングする
│  ├─ 対応可能者・判断者・補佐などを整理する
│  └─ 現行タスク管理体制との整合性を確認する
│ 
├─ サブカテゴリ設計
│  ├─ 業務分類のカテゴリ軸（例：ネットワーク、端末等）を定義する
│  ├─ 各業務をカテゴリへ紐付ける
│  └─ 対応ルールのベースとして整理する
│ 
├─ 担当者と代替者の役割定義
│  ├─ 1次対応、補佐、エスカレーション先の構造を整理する
│  ├─ 不在時対応・交代ルールを検討する
│  └─ 明文化・関係者レビューを行う
│ 
└─ 新業務体制・範囲の設計
   ├─ GoogleSheet / Notion など候補ツールを比較検討する
   ├─ 管理項目・レイアウト案を作成する
   └─ 継続運用可能なルール案を設計する

② レポートラインの構築（サブプロジェクト）
├─ 対象イベントの定義
│  ├─ 報告対象とするインシデント例・条件を整理する
│  ├─ 対象基準（頻度、影響度、部門横断性など）を定義する
│  └─ 対象外ケースも含め、基準をドキュメント化する
│ 
├─ 報告項目のテンプレート化
│  ├─ 報告内容（誰が・何を・どう）を整理する
│  ├─ Slack / フォーム等でテンプレート案を作成する
│  └─ フィードバックを受けて改善する
│ 
├─ ケース別フロー設計
│  ├─ 小規模障害・部署間連携などパターンを想定する
│  ├─ 各パターンにおける判断ステップを設計する
│  └─ 説明資料化しやすい形でまとめる
│ 
├─ レポート管理の方法決定
│  ├─ 保管場所（Notion, スプレッドシート）を選定する
│  ├─ 参照権限・編集ルールを整備する
│  └─ 引継ぎ活用を想定した形式にする
│ 
└─ トライアル運用
   ├─ 1週間〜2週間程度の試験運用スケジュールを組む
   ├─ 運用後フィードバックの回収項目を設計する
   └─ 改善点の取りまとめと次アクションの提示を行う

```

## プロジェクト進行上のスコープについて

### プロジェクトの目的

> 突発的なヘルプデスク対応の属人化を解消し、**業務処理速度の向上**と**チーム全体の負荷分散**を実現することで、各メンバーのプロジェクト遂行力とユーザー対応品質の両立を図る。
> 

主目的としては、下記2点

- **業務処理速度の向上**
- **チーム全体の負荷分散**

### 進行上の留意点

上記を達成するための手段については、まずは現行フローと共存可能な形を構築するが、今後のタスク進行において整備された運用状況や体制面のボトルネック次第では、DX推進部のリソース以外の活用も視野に入れる。（コストと価値を比較しながら、社外リソースやサービス、HILLTOP仕様のAIエージェントの作成などを実施する可能性を考慮）

# 🧱 新設計導入ステップ構成案（ステップ1〜3）

### ✅ **ステップ1：対応体制の構築（一部実施済み）**

> 「属人化を解消し、可視化された対応体制を構築するフェーズ」
> 
- ローテーション制の設計（Doer / Supporterの役割分担）
- 各ドメインごとのチーム体制設計（兼任・判断者除外など）
- 判断フローの整備（責任者→判断者のエスカレーション）
- ドキュメント／ガイドラインの整備（SLA, メンションルール）

---

### ✅ **ステップ2：リクエスト対応フローの整備と自動化設計**

> 「ユーザー投稿からタスク起票・判断までをスムーズに繋げるフェーズ」
> 
- Slackリクエストフォームの構成見直し（分類／サブカテゴリ／即時対応）
- Botによるスレッドヒアリング・担当通知の設計
- Notion連携でのヒアリング要約 → 起票テンプレートの整備
- 担当者無反応時の補佐対応自動化（1時間ルール）
- 判断フラグによるエスカレーションルート設計

    ## 🪜 フェーズ分解とタスク詳細（1.5ヶ月）
    
    ### **フェーズ1：現状整理と影響分析（1週）**
    
    - 各メンバーの日常タスク＋突発対応の実態調査
    - 既存の業務棚卸リストと役割一覧の収集
    - 業務毎に「処理難易度」「発生頻度」「依存関係」を分類
    - ※ヘルプデスクで頻出するインシデントのパターン抽出をここで実施
    
    📌**アウトプット：現状業務マトリクス / 属人度と業務負荷の可視化**
    
    ---
    
    ### **フェーズ2：RACI・業務分担の再設計（2週）**
    
    - 抽出された業務ごとに「責任者・実行者・支援者・報告先」をRACIで明確化
    - リーダーと協議し、各担当の負荷再配分案を作成
    - ヘルプデスク対応業務に関しては、交代制 or スプリント制による対応方式を試案
    - メンバー全員へのヒアリングと調整
    
    📌**アウトプット：新業務分担案 / 改訂RACIチャート / ヘルプデスク担当交代案**
    
    ---
    
    ### **フェーズ3：体制図とレポートライン・運用設計（1週）**
    
    - チーム体制図、業務グループマップを作成（図式）
    - タスク可視化ツール（例：Backlog, Trello, Excel）上で業務を記録・報告する簡便なルールを整備
    - 日次/週次レビューの方式とタイミングを定義（EXミーティング設置など）
    
    📌**アウトプット：業務体制図 / レポートライン設計図 / タスク運用ルール**
    
    ---
    
    ### **フェーズ4：検証・フィードバック・最終化（1.5週）**
    
    - トライアル運用（1週間）
    - 各メンバーからの所感ヒアリング（特にヘルプデスク突発対応の影響度）
    - プロセス改善案を取り込み、確定版の運用ルールと業務体制を作成
    - 関連プロジェクト（ナレッジ整備）へ業務定義とインシデント分類を引き渡し
    
    📌**アウトプット：確定業務体制 / 最終版RACI / ナレッジプロジェクト引き渡し資料**
